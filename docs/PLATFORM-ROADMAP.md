# План расширения платформ

Анализ по [issue #2](https://github.com/MimicBYE/AnimeTracker/issues/2), 26 октября 2026. База анализа — коммит `0400c616a7db9398555a78b8cb8de508ee20cbd8`, .NET SDK 10.0.403, Avalonia 12.1.4. Этот документ описывает будущие работы; Linux и мобильных пакетов сейчас нет. Требования и статус проверки — [SYSTEM-REQUIREMENTS.md](SYSTEM-REQUIREMENTS.md).

Обновление 28 октября, AT-20: по запросу владельца общий слой приложения выделен до Linux-порта. Windows и Avalonia используют TrackerService внутри Core: операции данных, обновления, пути, перенос/backup; AppStore стал адаптером системной папки и модальных окон. [Текущая архитектура](ARCHITECTURE.md). Это часть основы M0; потоковый импорт, мобильный lifecycle, XDG-пути, межпроцессная запись и новый UI остаются будущими этапами.

## Решение и порядок работ

Сначала подготовить Linux x64 на существующей Avalonia-версии, затем выделить общий слой приложения и сделать Android, после него iOS/iPadOS. Windows остаётся на WPF/.NET Framework 4.8; переписывать его ради портов не требуется. Общие модели и XML должны продолжать собираться компилятором C# 5 для Windows.

Для мобильного интерфейса использовать Avalonia с отдельными точками входа и навигацией. Это позволяет сохранить каталог, импорт, доменные правила и бумажное оформление. Прямой запуск desktop-окон на телефоне не решает задачу: нужны другие жизненный цикл, ввод и работа с файлами. Если прототип выявит проблемы доступности или производительности, пересмотреть выбор UI до переноса остальных экранов. Полная перепись на MAUI/нативный UI сейчас увеличит объём работ без подтверждённой пользы; Web/PWA и облачная синхронизация — отдельные задачи.

Первый Linux-выпуск: Ubuntu 24.04/26.04 LTS x64, X11 или XWayland; обычное приложение работает без трея и виджета. Нативный Wayland, другие дистрибутивы и ARM64 подключаются после отдельной проверки. Для телефонов начальная цель — Android 14+ ARM64, затем iOS/iPadOS 18+ ARM64. Это выбранная граница проекта, а не минимальный API, на котором теоретически запускается фреймворк. Совместимость определяется пересечением ограничений Avalonia, .NET, ОС и реально проверенного пакета. [Матрица Avalonia](https://docs.avaloniaui.net/docs/supported-platforms), [матрица .NET 10](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md).

## Целевая структура

Будущие каталоги; этот PR их не создаёт:

В AT-20 слой Application размещён в существующем Core для совместимости сборки C# 5; отдельный проект ниже остаётся возможным последующим разделением. UI/mobile-проекты пока не созданы.

```text
src/AnimeTracker.Core/          модели и совместимые правила, C# 5
src/AnimeTracker.Application/   операции библиотеки, импорт, refresh, очередность записи
src/AnimeTracker.UI/            общие Avalonia-контролы и модели экранов
src/AnimeTracker.Desktop/       desktop lifetime и адаптеры macOS/Linux
src/AnimeTracker.Android/       Activity, storage/share, фоновая работа
src/AnimeTracker.iOS/           iOS lifetime, storage/share, lifecycle
src/AnimeTracker.Windows/       существующий WPF-клиент
```

Выделять слои небольшими PR с сохранением существующего Mac-пакета. Общий `Core` не зависит от UI, мобильных workload или desktop API. Сервис приложения получает интерфейсы путей/хранилища, выбора файлов, расписания и возможностей платформы; не делать универсальный интерфейс для всех нативных функций сразу. Для Android Avalonia использует `IActivityApplicationLifetime` и фабрику представлений при пересоздании Activity; iOS — `ISingleViewApplicationLifetime`. Нужны сохранение состояния и идемпотентная инициализация, а не общий singleton окна. [Application lifetimes](https://docs.avaloniaui.net/docs/fundamentals/application-lifetimes).

## Этапы и оценка

Оценка в рабочих днях одного разработчика, знакомого с проектом: реализация, review, тесты и исправления в указанном объёме. Это диапазоны планирования без замеров/прототипов, без ожидания устройств, аккаунтов и проверки магазинов. Резерв на неизвестные нативные проблемы — ещё 30%. Этапы идут последовательно; общая мобильная основа учитывается один раз.

## Linux: детали решения

- Для первого выпуска использовать X11/XWayland. Avalonia 12.1 поддерживает отдельный opt-in Wayland backend, но `UsePlatformDetect()` сам его не включает. Нативный Wayland — отдельный этап с проверкой позиционирования, drag, DPI и возможностей композитора. Общего обещания «виден при Show Desktop» для всех Linux-оболочек не делать. [Linux backend](https://docs.avaloniaui.net/docs/platform-specific-guides/linux).
- Данные хранить в `$XDG_DATA_HOME/AnimeTracker` (по умолчанию `~/.local/share/AnimeTracker`); кеш — в `$XDG_CACHE_HOME/AnimeTracker`; настройки — в `$XDG_CONFIG_HOME/AnimeTracker`. Относительные XDG-пути игнорировать по спецификации. Ввести явные пути файлов вместо предположения об одной папке; backup собирает логический набор данных. Старый fallback переносить только после проверки и с сохранением исходника. [XDG Base Directory](https://specifications.freedesktop.org/basedir/latest/).
- Автозапуск — пользовательский `.desktop` в XDG autostart, только после включения пользователем; корректно экранировать Exec и путь с пробелами, не требовать root. В portable-режиме объяснить последствия перемещения каталога. [Autostart](https://specifications.freedesktop.org/autostart/latest/).
- Трей — необязательная возможность: проверить StatusNotifierItem/AppIndicator. В GNOME может потребоваться расширение. При отсутствии трея закрытие не должно оставлять недоступный процесс, а `--startup` должен иметь доступную точку открытия. [TrayIcon](https://docs.avaloniaui.net/controls/navigation/trayicon).
- Прототип виджета X11 с hints конкретного WM оценить отдельно, 3–5 дней. Если оболочка не поддерживает закрепление, явно показать ограничение и оставить отключаемое обычное окно. Wayland-интеграция — отдельное исследование 3–5 дней без гарантии универсального решения.
- Начать с `tar.gz` и проверки права запуска/нативных библиотек на чистой VM. AppImage/Flatpak — последующий этап (3–6 дней на выбранный формат) с проверкой sandbox, порталов, кеша и автозапуска. ARM64 — ещё 2–4 дня при наличии нативного runner/устройства. Alpine/musl и embedded не входят в первую матрицу.

## Мобильные платформы: отдельные ограничения

На телефоне первым результатом будет обычное приложение. Desktop-трей, постоянное окно поверх рабочего стола и LaunchAgent не переносятся. `DispatcherTimer` работает только в живом процессе: обновлять каталог при открытии/возврате и вручную, а фоновую работу планировать через разрешённые ОС механизмы без обещания точного интервала. Операции +1/статус/импорт должны завершать атомарную запись до возврата успеха; фоновые обновления не меняют личные поля. Повтор после process kill не должен удваивать +1 или повреждать XML.

Импорт: системный picker → ограниченный поток → временная копия в sandbox → существующий preview/merge → backup → commit. Не требовать общих прав на файловую систему и не полагаться на `TryGetLocalPath()`: Android может вернуть document URI. Для backup нужны ограничения размера/числа файлов, защита от Zip Slip/симлинков, предварительная проверка XML и сохранение предыдущей библиотеки. Совместимость ZIP-backup с мобильными — будущая функция; существующий экспорт ZIP пока не означает готовый универсальный restore. [Android Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files).

### Android

Добавить `net10.0-android`, Android workload и SDK/JDK, совместимые с выбранной версией workload; зафиксировать их в CI. `minSdk` первоначально 34 (Android 14), `targetSdk` определить по актуальным требованиям канала при выпуске. x64 используется для эмулятора, ARM64 — для первого устройства/пакета; ARM32 отдельно не заявлять. Ключ подписи хранить в защищённых release-секретах, не в репозитории. [Настройка Avalonia Android](https://docs.avaloniaui.net/docs/platform-specific-guides/android).

Виджет Android — отдельный `AppWidgetProvider`/RemoteViews, ориентир 5–8 дней после MVP: тайтл/обложка/+1/переход, размеры launcher, идемпотентная запись через общий сервис, тест конкурентного нажатия и ограничения фоновой работы. Не копировать Avalonia `WidgetWindow`. Периодический `updatePeriodMillis` ограничен минимумом 30 минут; реакция на действие пользователя — отдельное обновление. [App widgets](https://developer.android.com/develop/ui/views/appwidgets/overview), [обновления](https://developer.android.com/develop/ui/views/appwidgets/advanced).

### iOS и iPadOS

Добавить `net10.0-ios` с отдельным lifetime и UI. Для нативной проверки/подписи нужен Mac с совместимыми Xcode и iOS workload, физическое устройство и provisioning. Нельзя копировать desktop ad-hoc codesign из `build-macos.ps1`; это другой канал сборки и подписи. Версии Xcode/workload фиксировать совместимой парой и проверять требования App Store перед выпуском, не переходить на preview SDK ради устранения несовместимости. Публикация/TestFlight требует доступа владельца к Apple Developer/App Store Connect. [Avalonia iOS](https://docs.avaloniaui.net/docs/platform-specific-guides/ios), [загрузка сборок Apple](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds/).

Виджет iOS — отдельное SwiftUI/WidgetKit extension, ориентир 8–12 дней после MVP: App Group с минимальным снимком, timeline, переход в приложение; интерактивный +1 — отдельная проверка App Intents, блокировок и согласования записей с .NET-приложением. Не позволять двум процессам независимо переписывать весь XML. Расширение не работает непрерывно, обновления планирует система. [WidgetKit](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date), [TimelineProvider](https://developer.apple.com/documentation/widgetkit/timelineprovider).

## Проверка и выпуск каждой платформы

1. Синтетические библиотеки на 100, 1 000 и 5 000 тайтлов: одинаковые ID, статусы, прогресс, оценки, заметки, скрытия, очередь и арки после roundtrip. MAL XML/GZIP, повторный импорт, кириллица/японский, повреждённые данные и отказ записи; личные данные в CI не используются.
2. UI: поиск/выбор подсказки, +1, завершение, фильтры/сортировка после рестарта, обложки и offline, календарь, импорт/backup. Масштабирование, клавиатура/экранный диктор, touch, отмена сетевого запроса и память после многократной навигации.
3. Linux: GNOME без расширения трея и KDE; X11/XWayland, log out/in, пути с пробелами, несколько мониторов, 100/150/200% DPI. Xvfb smoke проверяет запуск, но не заменяет эту матрицу. Android: API 34 и актуальная поддерживаемая ОС, rotation/process kill/low memory; iOS: нижняя и рекомендуемая ОС, suspend/kill, iPhone/iPad.
4. Release-архив/подписанный пакет устанавливается на чистую систему без SDK. Выполняются замеры по [методике](SYSTEM-REQUIREMENTS.md#проверка-и-обновление-требований). CI сохраняет отчёт версии/устройства, логи без личных данных и checksums.
5. Desktop-публикация расширяет существующий общий комплект только после готовности платформы. Мобильные builds идут отдельными заданиями и каналами (APK/AAB, TestFlight), проходят тот же аудит зависимостей; отсутствие release-секретов не отменяет обязательную проверку сборки. Проекты с workload нужно отделить от обычного Core job и включить в аудит на подходящем runner. PR из fork не получает ключи подписи.

## Условия начала следующего этапа

Linux-прототип можно начинать без аккаунтов магазинов. До mobile release нужны реальные тестовые устройства и решение владельца о каналах распространения; до iOS — доступ к подходящему Mac и подписи. Сервер и автоматическая синхронизация между устройствами не предполагаются: сначала ручной перенос с backup, конфликтующие библиотеки автоматически не объединяются.

Предлагаемые следующие задачи: L0–L2 (Linux), M0 (общая основа), A1–A2 (Android), I1–I2 (iOS); нативные виджеты и дополнительные пакеты — отдельно. Этот анализ не создаёт эти issues и не означает, что перечисленные порты уже реализованы. При завершении каждого этапа обновлять требования и сохранять результаты проверки.
