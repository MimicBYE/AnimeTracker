# CI, ветки и автоматические релизы

## Когда запускается workflow

`.github/workflows/ci.yml` запускается при push в `main`, `dev`, `AT-*`, при pull request в `main`/`dev` и вручную. PR, ветки задач и ручной запуск выполняют только проверки. Публикация разрешена исключительно событию push в `main` или `dev`.

| Ветка | Пакет и тег | Публикация |
| --- | --- | --- |
| `main` | Версия из `VERSION`, например `v1.1` | Стабильный релиз, становится Latest |
| `dev` | Нормализованная версия и номер запуска, например `v1.0.0-dev.42` | Pre-release, не меняет Latest |
| `AT-1`, PR, ручной запуск | Проверочный комплект с версией приложения | Только Actions artifacts |

У уже выпущенной версии тег не перемещается и вложения не заменяются. Если `main` содержит прежний `VERSION`, проверки проходят, а выпуск нового релиза пропускается. Поэтому принятие инфраструктурного PR по issue #1 не заменит существующий релиз `v1.0`.

Номер запуска `dev` не меняется при повторном запуске того же workflow. Идентификаторы Actions artifacts включают номер попытки, чтобы не смешивать файлы разных попыток. Суффикс dev относится к пакету и GitHub-релизу; интерфейс приложения показывает обычную версию без метки тестовой сборки.

## Задачи CI

1. **Release plan:** проверяет согласованность версии в Windows, обоих проектах .NET и macOS; выбирает канал и номер пакета.
2. **Core:** на Ubuntu, Windows и macOS запускает тесты инфраструктуры и общей логики. Проверяются XML/GZIP-импорт, миграция библиотеки, статусы и серии, фильтры, заметки, арки, рекомендации и загрузка обложек через локальные HTTP-заглушки.
   На Windows/macOS также запускается `AnimeTracker.DesktopTests`: синтетические библиотеки 1000/5000, debounce/сохранение при закрытии, ограниченный viewport и прокрутка в прозрачном нативном окне. Linux UI эта проверка не заявляет. Выводит диагностические времена обработчиков; временные пороги не являются условием CI и не заменяют ручную проверку FPS/Mac UI.
3. **Windows package:** компилирует WPF, проверяет упакованный EXE, импорт и повторную сборку из распакованного source ZIP.
4. **macOS package:** на macOS собирает самостоятельное ARM64-приложение, применяет локальную ad-hoc подпись и проверяет её. Архив сохраняет Unix-права запуска.
5. **Dependency audit:** проверяет прямые и транзитивные NuGet-зависимости всех SDK-проектов. High/Critical, неизвестный формат отчёта и недоступная база блокируют проверку. JSON-отчёт сохраняется как Actions artifact. Эта же reusable workflow запускается еженедельно и вручную.
6. **Verify release bundle:** только после тестов, аудита и упаковки получает артефакты этого запуска и попытки, проверяет три архива, одинаковый коммит/версию/канал, отсутствие личных данных, структуру Mac-пакета и права 0755. Создаёт общий SHA-256.
7. **Publish release:** только после всех предыдущих проверок создаёт черновик, загружает Windows, macOS, source ZIP и `SHA256SUMS.txt`, сравнивает размеры и SHA-256 с ответами GitHub и публикует комплект целиком.

Отдельный **Dependency review** проверяет изменения зависимостей в PR и отклоняет новые High/Critical во всех scopes. Dependabot еженедельно открывает PR обновлений NuGet и GitHub Actions в `dev`; security updates GitHub могут направляться в основную ветку. Auto-merge не включён. Политика, приватный канал сообщения об уязвимостях и границы проверки описаны в [SECURITY.md](../SECURITY.md).

Официальные Actions закреплены полными SHA. SDK выбран в `global.json`. Проверки и упаковка имеют `contents: read`, checkout не сохраняет credentials. Только последний job получает `contents: write`; отдельный PAT не нужен, используется `GITHUB_TOKEN`. Workflow не использует `pull_request_target` и не запускает код из PR с токеном публикации.

Сборки `main`/`dev` не прерывают уже работающий workflow. Публикации дополнительно сериализуются. При конкурентном выпуске одной версии последний job повторно проверяет существующий тег и не меняет чужой коммит.

## Повторный запуск и ошибки

Готовый релиз того же коммита не меняется при retry. Черновик можно продолжить, только если его целевой коммит и уже загруженные вложения совпадают с текущими файлами по размеру и SHA-256. Если повторная компиляция дала другие бинарные байты либо черновик изменён, workflow останавливается для проверки владельцем. Автоматических удалений, `--clobber` и force-push нет.

Неуспешные проверки или несовпадение SHA-256 оставляют релиз неопубликованным. После исправления причины повторите workflow. Не обходите ошибки выдачей дополнительных прав или отключением проверок.

## Подготовка стабильной версии

1. Примите проверенные issue-ветки в `dev`.
2. Обновите версию через `scripts/set-version.ps1`, затем описание релиза и пользовательскую документацию.
3. Создайте PR `dev` → `main`, дождитесь CI и review.
4. После merge push в `main` автоматически соберёт и опубликует новый номер обеих платформ одним релизом.

Для первоначального внедрения PR по issue #1 направлен в `main`. `dev` создаётся от текущей `main`; после merge инфраструктуры обновите её из `main`. До этого в `dev` не будет нового workflow.

Рекомендуемые правила защиты для владельца: запрет прямого push и обязательный review/успешный CI для `main` и `dev`. Настройки защиты репозитория этот PR автоматически не изменяет.

## Ручная проверка

```powershell
./tests/Release.Tests.ps1
./tests/DependencyAudit.Tests.ps1
./scripts/check-dependencies.ps1
dotnet run --project tests/AnimeTracker.CoreTests -c Release
./scripts/release-windows.ps1
./scripts/build-macos.ps1
```

Windows-команды выполняются на Windows; локальная подпись Mac-пакета проверяется на Mac. PowerShell 7 нужен для общего скрипта упаковки macOS. В Actions он уже доступен.

CI не подтверждает удобство UI, работу рабочего стола Explorer/Spaces и автозапуска. Это ручные проверки на соответствующей ОС. Ad-hoc подпись Mac подтверждает целостность локальной сборки; она не является Developer ID или нотарификацией Apple.
