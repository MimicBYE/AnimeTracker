# Работа с проектом

## Задачи и ветки

Каждое изменение начинается с issue: проблема или цель, ожидаемое поведение и способ проверки. Пример для issue #12: ветка `AT-12`, коммит `AT-12: исправить восстановление виджета`, тело коммита `Refs #12`.

| Ветка | Назначение |
| --- | --- |
| `main` | Проверенные стабильные изменения |
| `dev` | Интеграция изменений и промежуточные сборки |
| `AT-<номер>` | Работа по одному issue; обычно создаётся от актуальной `dev` |

Обычный путь: `AT-12` → pull request в `dev` → проверки и review → merge. Для стабильного выпуска создаётся pull request `dev` → `main`. Прямые пуши в `main` и `dev` не используются в обычной работе. Срочное исправление от `main` требует согласованного с владельцем порядка переноса обратно в `dev`.

`main` и `dev` защищены на GitHub: обязательны PR, актуальная база, девять проверок CI и разрешённые обсуждения; force-push и удаление запрещены, правила действуют для admin. По решению владельца MimicBYE и QelBast могут самостоятельно сливать готовые PR без второго approval. Внешние участники предлагают PR из fork и не получают write по факту contribution; для их Actions требуется подтверждение запуска. Точные checks, права и границы — [защита репозитория](docs/REPOSITORY-PROTECTION.md).

Первоначальная настройка инфраструктуры в issue #1 — отдельное исключение: `AT-1` создана от `main`, первый PR направлен в `main`. Ветка `dev` создаётся от текущей `main`; после принятия первого PR её нужно обновить из `main`, чтобы включить тот же CI.

В PR укажите причину, итоговое поведение, проверки и `Refs #<номер>`. В PR в `main` можно использовать `Closes #<номер>`. GitHub автоматически закрывает issue по ключевому слову только при попадании PR в основную ветку; после PR в `dev` issue закрывается вручную после проверки результата. Не закрывайте issue до принятия изменения.

Выполненные подпункты отмечайте в чек-листе issue, сохраняя текст автора и новые требования. Отметка означает готовую реализацию с указанным PR и проверками; если она ещё не вошла в `main`, укажите это рядом. Автоматические PR Dependabot — исключение из имени `AT-N`: они рассматриваются отдельно и проходят тот же review/CI.

## Проверки

Для общей логики нужен SDK из `global.json`. Windows-приложение использует компилятор .NET Framework 4.8+.

При добавлении платформы, изменении зависимостей, упаковки или требовательных к ресурсам функций обновляйте [системные требования](docs/SYSTEM-REQUIREMENTS.md), README и release notes, если изменяется заявленная поддержка. Фиксируйте проверенное устройство/ОС и отделяйте измерения от предварительных бюджетов. Порядок будущих портов и критерии готовности — [план платформ](docs/PLATFORM-ROADMAP.md).

```powershell
./tests/Release.Tests.ps1
./tests/DependencyAudit.Tests.ps1
./scripts/check-dependencies.ps1
dotnet run --project tests/AnimeTracker.CoreTests -c Release
./scripts/release-windows.ps1
```

Последняя команда запускается на Windows и проверяет переносимый архив, XML/GZIP-импорт и сборку из распакованных исходников. macOS-пакет собирается PowerShell 7 и SDK .NET 10 на Mac либо кросс-сборкой из Windows:

```powershell
./scripts/build-macos.ps1
```

`sh scripts/build-macos.sh` — оболочка над тем же PowerShell-скриптом; нужен `pwsh` в PATH. На Mac проверяется локальная ad-hoc подпись. Это не Developer ID и не нотарификация Apple. UI, Show Desktop/Spaces и автозапуск проверяются вручную на соответствующей ОС.

## Версии и публикация

Версия приложения хранится в `VERSION`. Для её изменения используйте:

```powershell
./scripts/set-version.ps1 -Version 1.1
```

Скрипт синхронизирует метаданные Windows, проекты .NET и `Info.plist`. Обновите описание релиза и пользовательскую документацию в том же PR. Менять версию ради каждого коммита не нужно.

После push в `main` CI публикует стабильный тег `v<VERSION>`, если этот номер ещё не выпущен. При существующем теге другого коммита выполняются проверки, публикация пропускается. Опубликованный `v1.0` остаётся неизменным. Повторный запуск для уже выпущенного коммита также ничего не заменяет.

После push в `dev` создаётся `v<major.minor.patch>-dev.<номер запуска>`, например `v1.0.0-dev.42`, с отметкой Pre-release. Он не становится Latest. Суффикс относится к пакету; в интерфейс приложения не добавляются метки тестовой версии. `BUILD-INFO.json` связывает пакет с коммитом и каналом.

Один релиз содержит Windows ZIP, macOS ZIP, исходники и общий `SHA256SUMS.txt`. Публикация возможна только после всех проверок. PR, ветки `AT-*` и ручной запуск CI ничего не публикуют. Подробности — [инфраструктура CI](docs/CI.md).

## Данные и лицензия

Требования безопасности и приватная отправка сообщений об уязвимостях — [SECURITY.md](SECURITY.md). High/Critical в зависимостях блокируют выпуск; не подавляйте advisories и не отключайте аудит ради успешной проверки.

Не коммитьте `data`, обложки пользователей, импорты, локальные резервные копии, токены, SDK и промежуточные сборки. Для тестов создавайте отдельные данные в `artifacts` или временной папке. Сохраняйте совместимость XML и пользовательский прогресс.

Лицензия собственного кода пока не выбрана. Атрибуция справочников и лицензии сторонних компонентов должны сохраняться в исходниках и пакетах.
